# Agent-name search: pipeline read API contract (v1), 2026-11-09

Status: v1 contract, implemented on branch feat/agent-name-search behind the flag `READ_API_AGENT_MATCH` (default off) with migration `supabase/migrations/20261105050020_session_directory_agent_match.sql`. Written 2026-11-09 against main dab11329.

Implementation notes: the migration adds a 17-argument overload of `sessions.list_session_directory_for` with no argument defaults (a default on `p_agent_match` would make 16-argument named calls ambiguous, and PostgreSQL forbids a required argument after defaulted ones), so callers name all 17 arguments; exact matching keeps calling the 16-argument function. The optional `READ_API_AGENT_MATCH_WORKSPACES` allowlist is not implemented in v1.

## What exists today (no change needed for exact match)
- Stored name: sessions.session_directory_agents (one row per agent per session, all agents) and session_directory.agent_name / agent_name_normalized (first agent only). Value = the uploader's `payload.agent_name` from the delivered session record, copied verbatim (relayhistory-projection.ts:671-707; session-directory-catalog.ts:189-191, 341-367). No `@` splitting, no harness mapping; some desktop fixtures send a harness kind ("codex") as the name. Written only when SEARCH_INDEX_ENABLED=1 runs the search stage; never written for Relay journal turns (per-turn actor_name only), buffered sessions, or legacy sessions without a redelivered catalog.
- Route: GET /v1/sessions?workspace=<id>&agent=<name>[&limit&source&notSource&user&projectContains&lastTsAfter/Before&firstTsAfter/Before&cursor] (src/session-read-api/app.ts:876-937). `agent` is single-valued, trimmed, <= 200 chars, matched case-insensitively (lower(btrim)) by EXACT membership in session_directory_agents through sessions.list_session_directory_for (directory.ts:100-120). Sorted newest first (last_activity_at desc), cursor pagination, workspace pinned to the token, SQL read-only. Buffered rows are excluded whenever `agent` is set. Before the catalog rollout is marked complete the route answers 501 `agent_filter_not_ready`.
- GET /v1/events answers 501 `param_agent`. No other route takes an agent filter.
- The hosted relayhistory-cloud recall route also takes a single exact `agent` (its ClickHouse paths refuse it); that repo is relayhistory-cloud-owner's.

## v1 contract (one agent per request)
- Client parses the search box: the first `@token` is the agent filter; later `@tokens` are ignored and the UI says "one agent at a time". Token charset: letters, digits, `-`, `_`, `.`, `@`. The rest of the query is free text sent as before (q / search are 501 on /v1/sessions today, so free text goes to the existing search path, not this route).
- Exact: `GET /v1/sessions?workspace=W&agent=<name>` (works on today's backend). Match is case-insensitive exact, no node stripping: send the token as typed minus the leading `@`. Do not strip an `@node` suffix in v1; the stored name is literal and no row shape evidence exists yet (a count-only probe over session_directory_agents is proposed; it is a production read needing Khaliq's OK).
- Prefix (new, behind the flag): `agent=<prefix>&agentMatch=prefix`, or `agent=<prefix>*` (the whole trailing run of `*` and whitespace is stripped server-side and the request is treated as prefix; `agentMatch=exact` together with a trailing `*` is 400). Prefix needs >= 3 meaningful (non-whitespace) characters after stripping, else 400. More than 5000 matching agent rows in the workspace (the budget counts (session, agent) rows in session_directory_agents, not distinct agent names) is 54000, mapped to 400 `agent_prefix_too_broad`. With the flag on but migration 050020 not applied, a prefix request answers 501 `agent_match_not_migrated` and exact requests are unaffected. `agentMatch=exact` is accepted and is the default. Repeated `agent` stays 400 (single-valued in v1).
- Flag: `READ_API_AGENT_MATCH` (default off; on only for the exact string "true"); an optional `READ_API_AGENT_MATCH_WORKSPACES` allowlist was proposed and is not implemented in v1. Off = today's behaviour exactly, and any `agentMatch` or trailing `*` returns 501 `unsupported_by_backend` reason `param_agentMatch`.
- Capability detection: the new backend echoes `X-Sessions-Read-Agent-Match: exact|prefix` on /v1/sessions responses when the flag is on, and adds it to `Access-Control-Expose-Headers` only then (flag off, the CORS expose list is unchanged). An OLD backend silently ignores `agentMatch` and matches `foo*` literally (empty 200), so a client that asked for prefix MUST treat a missing header as unsupported and discard the page; recommended UI: hide the `*` form until the header is seen.
- Ordering: `@name` alone = `agent=name` with no other filter, newest first (already the route's order).
- Scope: the filter only narrows the already workspace-scoped query; per-user G2/privacy and canonical-vs-buffered rules are unchanged (buffered rows drop out whenever an agent filter is present, as today).
- Roster for autocomplete: none today. Proposed follow-up `GET /v1/agents?workspace=W[&prefix=&limit=]` returning `{agentName, lastActivityAt}` newest first from a GROUP BY over session_directory_agents, own read-API function, own default-off flag, workspace-scoped.
- OR of several agents: v2, a text[] parameter on a new function version after the schema freeze lifts; no client-side union.
