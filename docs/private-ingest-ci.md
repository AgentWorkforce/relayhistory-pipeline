# Guarded private-ingest CI route

**FUTURE DRAFT — NOT RUNNABLE FOR A MUTATING DEPLOY.** The live repository billing plan cannot enforce required-reviewer environments; this route must fail rather than use the partially created unprotected environment. The installed Alchemy CLI also requires --yes for noninteractive changes, and --yes can create/upgrade its state-store Worker. This draft intentionally omits --yes. A separately reviewed safe apply adapter/state prerequisite and real GitHub protection/live CI proof are still required. No dispatch or apply is authorized.

This is source for a future operator-run dark deploy of the private `96bulls-session-ingest` Worker. It does not authorize a workflow dispatch or change live configuration. The original guarded Alchemy config, plan contract, resource declarations and private-Worker invariants are consumed unchanged. There is no alternate Wrangler deploy or manual configuration patch.

## Required preparation by the operator

The existing environment `session-ingest-worker` must be created and protected by a human before this workflow can run. The first job deliberately has no environment reference, so a missing name cannot silently create an unprotected environment. Its read-only GitHub API checks require exactly one named human reviewer (not a bot/team) and a custom deployment branch policy allowing only the `main` branch, not a matching tag. The protected job rechecks the configuration and the current run's actual approval history before any Cloudflare operation. Re-runs are refused: dispatch a new run so approvals cannot be reused across attempts.

Set repository variable `SESSION_INGEST_APPROVER_LOGIN` to the verified GitHub login of the human owner approving this rollout. This identifies an existing human; the workflow does not create an identity or grant access.

The protected environment needs non-secret variables `SESSION_INGEST_ACCOUNT_ID`, `SESSION_INGEST_HYPERDRIVE_ID`, `SESSION_INGEST_SECRETS_STORE_ID` and `SESSION_INGEST_KMS_KEY_ARN`. Their actual values and authority are operator prerequisites, not inferred from names. The environment secret `CLOUDFLARE_API_TOKEN` is supplied only to the final guarded Alchemy step, after installation and human approval checks. It is never written to a capture file, printed or passed as a command argument. GitHub API checks use the run's `actions:read` token.

The operator must independently verify the same-account Hyperdrive target, transaction-pooler role/TLS/cache policy, Supabase role/schema readiness, Secrets Store descriptors and existing S3 writer authority. The workflow creates none of these prerequisites. A successful source test or plan does not prove them. A plan uses Cloudflare-backed Alchemy state. Under the installed CI behavior, a missing or outdated state store refuses without --yes; this draft never supplies that flag. A compatible existing reviewed state store is a separate prerequisite, and the capture acknowledgement does not create or upgrade it.

## Capture, review and deploy

1. Merge the reviewed source through the normal process. The workflow runs only from `main`; `expected_source_sha` must equal the immutable workflow/checkout SHA. Any source change requires a new capture.
2. Manually dispatch `guarded private session-ingest Worker` with phase `capture`, the exact main SHA, and `acknowledge_state_ready=true`. Leave deploy-only inputs empty. The human approves the protected environment job after reviewing the source and prerequisites.
3. The adapter renders credential-free inputs (replica mode remains off), runs the existing Alchemy compact and detailed plans, applies the existing four-resource/action/credential plan contract, and uploads a seven-day immutable Actions artifact. Only validated plans, sanitized inputs and provenance are uploaded. Failed command stdout/stderr is never echoed. Capture failure publishes no artifact.
4. Review both plans, exact inputs, source SHA and provenance. Record the printed capture hashes. The approval JSON must be the operator's real, dated verbatim approval, using the original `decision/by/date/quote/capture` shape; the workflow never manufactures that approval. For example, the schema is `{decision,by,date,quote,capture:{provenanceSha256,planSha256,inputsSha256,sourceCommit}}`. Copy the exact hashes from the reviewed capture, not placeholders.
5. Dispatch a NEW run at the SAME unchanged main SHA with phase `deploy`, `capture_run_id`, `capture_provenance_sha256` and that approval JSON. The named human must approve this protected job separately. If main has advanced, recapture at its new SHA instead of relaxing the revision check.
6. Before download/deploy, the adapter checks that the prior capture run is successful, same repository/workflow, workflow_dispatch on main, first attempt and exact source SHA. It validates all compact/detailed/input/provenance hashes and the original bound approval contract. Current protected-environment input values must have the same input digest; environment/reviewer IDs and captured Node/Bun/Alchemy versions must also match. A fresh compact AND detailed Alchemy plan must match the reviewed bytes after the established timestamp/ANSI normalization. Drift refuses before deploy.
7. The current FUTURE-DRAFT source attempts the existing guarded `alchemy deploy`. The stack validates the approval and plan contract again. Because the installed CLI requires --yes for changed plans, a mutating deploy currently refuses; this is an explicit implementation/readiness gap, not an approval bypass. No upstream delivery binding, DELIVERY_FORWARD flag, source export/seed, database migration, IAM or Secrets Store mutation is performed. Read-only postchecks require workers.dev and previews disabled and no custom domain for the exact Worker.

A changed source/input/capture/plan, expired or mismatched approval, missing human protection, missing API access, failed private-surface check or failed command is RED. The workflow does not work around a rejection or automatically retry a mutation.

## Evidence and limits

Offline tests inject synthetic GitHub/Cloudflare/Alchemy capability ports and prove command ordering: invalid gates perform zero Cloudflare/Alchemy operations, valid deploy performs two fresh plans then one existing Alchemy deploy, and modified detailed plans/input/capture/authority refuse. Existing stage mutation/private-surface and ingest ledger/seed/bundle tests remain active. The CI test harness allows 30 seconds per test because the unchanged role-bootstrap fixture initializes three PGlites sequentially (the strict four assertions completed in 13.43 seconds on the measured SF run); application deadlines are unchanged. These tests do not establish live environment protection, actual current-run approval, prerequisite resources, Alchemy output stability or a successful deployment. Those need real CI evidence on the exact merged revision, obtained only by an authorized operator.

The postchecks cover workers.dev/previews/custom domains. The declared plan still forbids routes and any public surface; independent account route inventory remains an operator check. No public 404 is treated as proof of a private Worker or of an installed deploy.

Failure after a successful apply needs an operator decision; this workflow does not destroy a production stage or run a second mutation. Keep DELIVERY_FORWARD off while resolving it. Roll back with a separately reviewed, freshly captured in-place Alchemy update; the original stack refuses replacements/deletions/destroy.

GitHub API contracts: [environments and required reviewers](https://docs.github.com/en/rest/deployments/environments), [current-run review history](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run). Cloudflare readback uses the exact Worker [domain filter](https://developers.cloudflare.com/api/resources/workers/subresources/domains/methods/list/).
