# Portable Lambda service composition and artifact

This is source and local-artifact preparation. It creates no cloud resources,
grants, schedules, deployments or publications. The existing exported Lambda
handlers retain their Supabase/ClickHouse behavior when no reviewed composition
is supplied. Setting an adapter name does not install an implementation.

## PostgreSQL TLS

Both pipeline and read-API pools use the same TLS policy:

- Unset `SESSION_POSTGRES_TLS_PROFILE`, or `supabase`, uses the existing pinned
  Supabase CA. Additional CA settings with that profile are refused.
- `custom-ca` requires `SESSION_POSTGRES_CA_FILE` and
  `SESSION_POSTGRES_CA_SHA256`. The latter is the approved file's exact SHA-256;
  the file contains only currently valid CA certificates. This is an explicit
  file reference, without credential/provider discovery.
- Missing/unknown profiles, missing/malformed/unapproved CA files and URL target
  overrides fail closed. URL TLS/options parameters cannot replace the explicit
  pool TLS policy. Certificate and hostname verification stay enabled.

The existing secret field names (`hoopdb_url`, read API `supabase_url`) are kept
for compatibility; their PostgreSQL URLs target the explicitly selected provider.
Credentials still arrive through the existing secret loader. CA trust does not
make a database schema/bootstrap profile compatible with RDS or Aurora.

## Explicit composition

`SearchComposition` supplies a public registry and a completeness-state factory.
The writer calls the selected adapter's scan/upsert/delete/erase operations;
the reader calls its query operation. Both require versioned, immediately visible
writes, synchronous erasure and the complete filter contract. Unsupported or
unregistered selections and incomplete bindings are refused. There is no SQL
emulation, provider discovery, fallback to ClickHouse, or private build import.

`createPostgresSearchComposition({backendId, fromMs})` composes the existing public
Postgres search implementation with epoch-fenced Postgres state.
`SEARCH_INDEX_BACKEND=postgres` explicitly selects it in an entrypoint that passes
this composition. `SEARCH_INDEX_POSTGRES_SCHEMA` selects the index/state schema.
Calling the default handler with `SEARCH_INDEX_BACKEND=postgres` still refuses it;
the default handler has no newly selected composition.

A reviewed entrypoint can register another implementation and supply the same
state interface. Provider endpoints, credentials, deployment policy and identities
remain explicit composition inputs. `SearchFactoryInput.secrets` comes from the
optional `search` string map in the existing service secret; it is never read from
the build host. Composition code can pass an explicit credential-provider/client
in `extras`. No private provider implementation is included or relocated here.

### Completeness and bootstrap

An index alone cannot say that a canonical projection is complete.
`SearchProjectionState` supplies a coverage floor, scope result recording and
tenant-bound partial/unknown checks. The read history floor must cover the
current index floor; a later retention-floor change refuses reads that would
otherwise omit history. Unknown or overflowing partial checks never admit a
complete answer.

The optional `postgresSearchState` helper stores content-free state by
backend/org/workspace/source/session, records the canonical directory epoch in
the writer's locked transaction, and checks it against current pointer scopes
and directory readiness. Missing state/directory, a changed canonical identity, a different epoch, a partial
pass or a different coverage floor refuses completeness. Equal per-directory epochs
on different canonical sessions do not establish the same projection identity. A first failed pass
with no index row is included in the check. Metadata counts continue to come
from canonical projection; index-window counts never replace directory counts.

Its `ensureSchema(owner)` is an explicit owner-bootstrap step. Services never
call it, and it issues no grants. It creates only the selected schema's
`projection_state`, forces tenant RLS, and rejects an unexpected policy set.
Initialize the index separately with its explicit `ensureSchema` operation and
preinstalled `pg_trgm`. No existing migration, compiled generation or protected
source pin is regenerated by this helper.

The new profile needs schema-owner review before any real installation:

- Writer: the existing source/directory access plus state insert/update/select
  and index select/insert/update/delete, with the exact transaction-bound tenant
  settings used by the helper and the index (index statements must run inside
  the writer's scope transaction).
- Reader: SELECT on the derived index and content-free state, and the pointer
  identity/canonical/deletion and directory identity/epoch/readiness columns
  referenced by the state query. Reader state and index calls use
  `TenantRunner`; the derived index has the same forced `tenant_only` RLS, so
  the reader login must be NOSUPERUSER NOBYPASSRLS (the self-host read service
  refuses to start otherwise).
- Existing legacy role grants do not establish these privileges. A missing
  privilege fails; this code never broadens a live role to work around it.

The writer keeps scope/canonical advisory locks, canonical folding, busy-scope
requeue, incomplete/truncated-read deletion refusal, metadata epoch checks and
SQS partial failures. A version-refused upsert marks the pass incomplete and
does not delete against the stale snapshot. Portable reads retain verified
tenancy, keyset order, byte-budget resume, erasure filtering, partial/history
refusals and bounded failures.

### Runtime binding

`createPipelineLambdaHandler({search, runtime})` is a separate reviewed
composition. When `runtime` is provided, `PIPELINE_RUNTIME=lambda` must be
explicit and the registry must actually contain a compatible Lambda binding.
The runtime adapter invokes the existing service work; S3 identity/deletion,
partial failures, busy requeue and reconcile continuation data remain attached.
Failed selected-runtime schedules request platform retry. Unknown or malformed
acknowledgments cannot silently acknowledge an SQS batch.

No public Lambda/SQS provider implementation is added by this change. Provider
conformance is separate from the test-only platform driver used by unit tests.
The default handler's existing dispatch path remains available unchanged.

## Local ZIP build contract

Use this checkout's own frozen installation and Bun 1.4.2, then build from an
exact clean canonical commit:

```sh
bun scripts/build-lambda-artifact.ts --service pipeline --source-sha FULL_SHA --architecture arm64
bun scripts/build-lambda-artifact.ts --service read-api --source-sha FULL_SHA --architecture arm64
```

Each dedicated `dist/lambda/` output contains a ZIP and `receipt.json`. ZIPs use
Node 24, `index.handler`, an ESM `index.mjs` with dependencies bundled, root
LICENSE/NOTICE, and the embedded schema generation/verifiers plus a hashed asset
inventory. Fixed ZIP ordering/timestamps/modes make repeated builds under the
recorded builder comparable. The receipt records source SHA, Bun/host identity,
lock/bundle/archive hashes, base64 `source_code_hash`, architecture and schema
inputs. The archive hash is outside the ZIP to avoid a circular identity.

`--allow-dirty-test` marks development builds as test-only; it also allows public
fork tests without claiming canonical provenance. These are not release receipts.
Output paths may not escape `dist/` or traverse symlinks. The official clean build
checks the original repository remote; release verification must additionally
bind actual canonical CI/repository identity and dependency installation.

The versioned `agent-relay-lambda-composition-v1` ABI exports public registry,
service and state constructors for a reviewed composition packaged with this
immutable artifact. A provider composition must name its own implementation
version/source, engine archive identity and exact handler/package identity.
Customers consume built immutable packages, without an implicit source checkout.
The current builder bundles no external provider and labels its default service
as legacy ClickHouse. Its ZIP cannot be advertised as OpenSearch-ready merely
because the ABI can accept an adapter. Private provider placement/distribution
requires its own decision; no private `.engine` checkout qualifies as an artifact.

The services OCI image has a different entrypoint and is not a Lambda package.
These local ZIP receipts are unsigned build records. No registry push, signing
workflow, Lambda upload or publication follows from this builder.

## Validation and limits

Tests cover actual TLS handshakes (approved CA/hostname and negative cases),
Postgres-backed canonical projection/read API, stale versions, retraction,
erasure, partial/epoch/floor checks, RLS, cursor/byte-budget continuation and
runtime envelope failures. Archive tests extract and import the installed code
under Node, remove copied SQL assets to prove embedding, exercise SQS/schedule
and HTTP envelopes, and compare repeated archive hashes.

`scripts/proof-portable-lambda-artifact.mjs` is for the isolated disposable
Linux arm64 / Node24 / PostgreSQL17 TLS fixture. It refuses other target shapes.
It tests installed ZIP service assembly, TLS refusals, real registered Postgres
queries, JWT audience/tenant refusal, pagination, a SELECT-only reader,
epoch-based partial refusal, SQS partial responses, default-off schedules and
synchronous tenant erasure. It does not validate a full HoopDb bootstrap or AWS
Secrets Manager/S3/SQS/Lambda/OpenSearch identities. It is not a cloud proof.

Provider repin/conformance, approved RDS/Aurora bootstrap, a distributable
OpenSearch implementation, the final composed artifact/signatures, and actual
private RDS/OpenSearch/Lambda/full-suite execution remain distinct acceptance
records. Historical provider-draft results and Unicode failures are not cleared
by these public-interface or Postgres tests.
