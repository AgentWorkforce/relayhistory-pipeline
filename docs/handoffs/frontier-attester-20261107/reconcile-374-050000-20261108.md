**(f) Canonical form.** P:217-241 (`frontierCanonicalJson`) works like this:
```
if (typeof input === "number") { if (!Number.isSafeInteger(input)) throw new Error("frontier_non_integer_number"); return input; }
for (const key of Object.keys(object).sort()) { ... out[key] = visit(object[key]); }
return JSON.stringify(visit(value));
```
- This gives sorted keys, compact JSON.stringify, bigint values as decimal strings, and unsafe numbers rejected. That is consistent with the v3 "sorted-compact" form (plan log 1271-1272).
- Two caveats. `Object.keys().sort()` uses UTF-16 order, which is not byte/C order (it only matters for non-ASCII keys; the keys are ASCII today). And sourceFrontier/recordFrontier are domain-tagged only by
  the protocol field, not by the dc068aef `publication-source-frontier-v1` / `publication-record-maxima-v1` prefixes.
- The receipt domain uses a second form: length-framed `first-ack-seat-domain-v1\n` with `row:` and `len:value` / `-1:` for null (C:64-76).
- Matching the component-key/bigint vectors **cannot be verified**, because fd3f8908 and 867f6b35 are not on this host (P1: run them before 050000 consumes the client).

**(g) `sessions.ingest_scoped_publication_receipt_capture_v1(jsonb)`.**

  (main, #321, the 049 design branch and the attester design all return no hits). It was introduced in 9438a2e7.

  name this RPC. A slot must be assigned (see i-4).

**(h) Trust placement.**
- Proposed placement: the function is STABLE SECURITY DEFINER, owned by postgres (C:140, D:32-37) and has search_path pinned. It runs as the owner when executed by the NOLOGIN NOINHERIT `bulls96_session_ingest_seeder` (C:26, C:136-140).
  It writes nothing; the client transaction is READ ONLY (C:133).
- Comparison with 049000: the only runtime EXECUTE grant is `bulls96_session_ingest` (R49:31), and the seeder's scope-capture grant is explicitly "not a receipt-read capability" (R49:113).
  The packet assumes no seeder broadening (packet :35).
- Comparison with 050000/dc068aef: the preparer makes no role or schema changes (A:14), and future automation needs a separate NOLOGIN boundary with no seeder reuse (A:16). The attester is a distinct NOLOGIN role (051000:114).
- Effect: #374's placement broadens the seeder with an owner-privileged read, which contradicts A:16 and packet :35. Main does have a precedent (seeder EXECUTE on ingest_seed_scope_capture/page,
  acl json :794-800).
- Recommendation: either use a dedicated NOLOGIN `*_receipt_reader` role, or obtain an explicit owner and Root waiver for seeder reuse.
