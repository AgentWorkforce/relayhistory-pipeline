## What changes

* `sessions.buffered_session_stages_for` (one session's detail) drives its `stg` from the claims whose
  `records` contain `(source, session_id)`, through the new GIN, instead of from the user's whole outbox.
  This is the RPC that timed out for the 167k-backlog owner.
* `sessions.buffered_sessions_for` (the list): same visibility, three quadratic CTEs removed (`recn` window,
  `bad_stage` hashed and MATERIALIZED, `per_session` reads back by primary key). Still linear in the backlog.
* Both: same signature, return type, STABLE, SECURITY DEFINER, `search_path`, owner and ACL (CREATE OR
  REPLACE, no GRANT or REVOKE). Every privacy, reset, deletion, owner, admission, lazy-ACK and native-slot
  predicate is kept verbatim (the PGlite parity test runs the 043700 bodies side by side over every fixture
  state). The reader (read API Worker) stays on its current build: no TS change is needed.
* #428 (`READ_API_OWNER_BUFFERED_INDEX_VERIFY`, default off) verifies only the outbox index
  `ingest_buffer_outbox_user_buffered_idx`. It does not know `ingest_claim_attempts_records_gin_idx`.

## Does a body replacement move the generation? (evidence)

* `generation()` hashes migration FILES, not catalog bodies: `src/hoopdb/migrate.ts:356-385` (sha256 over
  every step name plus the file's sha256, plus the verifier files). Adding the 044040 file to the image
  moves it, whatever its content. A CREATE OR REPLACE run outside the migrator does not.
* The parity gate pins the readiness marker's PASS generation, never a function body:
  `owner_buffered_parity_expected` reads `__96bulls_role_validation.generation WHERE status = 'pass'`
  (`supabase/migrations/20261105043700_owner_buffered_read.sql:257-260`); `owner_buffered_read_scope` opens
  only when that is non-NULL and equals the stored proof's `target_generation` (same file, `:375` and
  `:383`). No prosrc is read anywhere in 043700 (its only `pg_proc` read, `:864`, is the ACL revoke loop).
* The 044030 overlap covers only the ingest fences (`ingest_require_generation`, `ingest_lazy_guard`;
  `supabase/migrations/20261105044030_ingest_generation_overlap.sql:36-44`), never the reader scope.
* So: via the migrator (packet B) the generation moves; the marker is `pending` from the first step
  (`MARKER_PENDING_SQL`, `migrate.ts:406`) so `target_generation` is NULL and every owner_buffered read is
  gated closed (empty) until PASS, and after PASS every stored G2 proof names the old generation and stays
  closed until re-proven. Via an out-of-band owner CREATE OR REPLACE (packet A) the generation does not move
  and the existing G2 proofs stay valid.
* The catch for A: the 044040 catalog sentinel (`src/hoopdb/migration-sentinels.ts`, the
  `BUFFERED_STAGES_SESSION_FIRST_STEP` entry) is the replaced BODIES, `count(*) = 2` over both readers with
  the `count(*) OVER (PARTITION BY rc.stage_token, rc.ord)` text, and for a step that replaces functions it
  is never overridden by index adoption (`src/hoopdb/migrate-guards.ts:1417-1422`). If both bodies are
  replaced out of band, the next migrate refuses with `unledgered_schema` (`migrate-guards.ts:1432-1438`),
  UNLESS both live bodies are byte-identical to this file's `$buffered_sessions$` / `$buffered_stages$`
  bodies with plpgsql, SECURITY DEFINER, STABLE, the file's `search_path` proconfig and the migrating
  role as owner (exact-body adoption, `migrate-guards.ts:1429-1431`, `exactBodiesLive`; declared in
  `migration-sentinels.ts` `exactBodies`). Then the step runs normally and writes its ledger row.
  Replacing ONLY `buffered_session_stages_for` leaves the sentinel false (1 of 2), so B later applies 044040
  normally (CREATE OR REPLACE is idempotent for the stages body).

A2. The one CIC (outside a transaction block):


Budget: a jsonb_path_ops GIN reads the heap once and is typically a fraction of the heap size. Set the
wall-clock budget from A1 (about 1 minute per GB of heap, minimum 5 minutes, cap 30 minutes); watch it
read-only with `SELECT phase, blocks_done, blocks_total FROM pg_stat_progress_create_index;`. CIC first waits
for older transactions, so a long-open transaction delays it (it takes no lock that blocks writers or
readers). If the budget is exceeded, cancel with `pg_cancel_backend` on that pid. A cancelled CIC leaves an
INVALID index: the migrator never adopts it (it RAISEs), and dropping it (`DROP INDEX CONCURRENTLY`) needs a
separate OK.

## Packet B: ledgered apply (044030 then 044040)

B0. The index must exist first (A2), or the migrator's read-only preflight refuses the whole run with
`index_prebuild_required` before any write (absent index on a populated `ingest_claim_attempts`; the only
override is `HOOPDB_ALLOW_BLOCKING_INDEX_BUILD=true`, a blocking build, not for production). An existing
valid index with the exact definition is adopted; an INVALID or different one RAISEs, nothing dropped.

B1. Apply order. `migrate.ts` applies every pending slot in one window. The ingest side follows
`docs/design/zero-503-schema-windows.md`:
* Window 1 (the one accepted outage, §3.1): the owner apply pinned to a source commit that contains 044030
  and NOT 044040. Pending union from the G4 ledger (last applied 043800): 043850, 043860, 043870, 043880,
  043890, 043900, 043910, 044000, 044010, 044020, 044030. 044030 cannot protect its own bootstrap (its
  window tables do not exist until it commits). Upload refusals (55000) last from the pending marker write
  until PASS plus the rebind (§3.1 steps 3-4). Report that interval (marker pending timestamp to rebind
  commit) instead of promising zero 503s.
* Window 2 (§3.2, overlap-protected for ingest): 044040 alone, Worker deployed with the overlap generation
  first, the overlap opened, apply, rebind.
* If both ride one window (a source commit that contains 044040 is applied while 044030 is pending), the
  pending union is the list above plus 044040, all inside the single §3.1 outage. Report it the same way.

B2. Reads during every window: `owner_buffered_read_scope` is closed from the pending marker write (PASS
generation NULL) and stays closed after PASS until the G2 proof is re-proven.

B3. G2 re-proof (after each window's PASS and rebind, before any canary): each owner's
`sessions.owner_buffered_parity` row must be re-proven against the current head / CAS and written with
`target_generation` = the new PASS generation, through the normal G2 proof path. No relabelling of stored
proofs: never UPDATE `target_generation` (or any other column) of an existing proof to the new generation;
a proof is valid only for the generation, head, baseline and digests it was computed at. Until re-proven,
reads for that owner return empty (gate closed), not stale data.

B4. Verify: A4's EXPLAIN; `SELECT count(*) FROM pg_proc WHERE prosrc LIKE '%count(*) OVER (PARTITION BY rc.stage_token, rc.ord)%' AND pronamespace = 'sessions'::regnamespace;` is 2; the ledger row
`upstream:20261105044040_buffered_stages_session_first.sql` exists.

B rollback: apply the down file (CREATE OR REPLACE both readers to the 043700 bodies). The index stays.
The rollback is itself a generation-neutral body change (no file is added), but the ledger then records
044040 while the bodies are 043700; a re-apply needs the ledger row removed under a separate OK.
