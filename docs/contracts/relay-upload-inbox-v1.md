# Contract: relay-upload-inbox-v1, desktop uploads straight to S3

Status: **frozen for implementation** (decision [`0004-direct-upload-inbox.md`](../decisions/0004-direct-upload-inbox.md)). Code only: nothing in the ingest path reads it yet, and every runtime piece stays behind `HISTORY_UPLOAD_DIRECT` (default `off`).

One definition for three parties:

- **relay-control** mints short-lived upload credentials and a signed witness.
- **relay-desktop** PUTs one object per delivery batch under the tenant's upload-inbox prefix, then polls the admission status.
- **this pipeline** (the hosted consumer Lambda or the self-host scan) re-validates, re-scrubs and admits each object through the existing async-admission path.

The reference implementation is [`src/session-ingest/upload-inbox-contract.ts`](../../src/session-ingest/upload-inbox-contract.ts): pure TypeScript, only `node:crypto`, no S3, no HTTP, no env reads. Other repositories pin to this document, to the vectors, and to that module's exported names.

Test vectors: [`relay-upload-inbox-v1.vectors.json`](relay-upload-inbox-v1.vectors.json). They are generated by `buildVectors` in `src/session-ingest/__tests__/upload-inbox-contract.test.ts`. That test regenerates them on every run and fails unless the result is byte-identical to the checked-in file. To change them on purpose, run it with `UPDATE_UPLOAD_INBOX_VECTORS=1`. All ids in the vectors are synthetic. **The witness key in the vectors is test-only (bytes `0x00..0x1f`) and must never be configured anywhere.**

"Upload inbox" is the name everywhere in this repository. The desktop's local `delivery_quarantine` table is a different thing. So is the `96bulls/upload-inbox/v1` candidate root in `stacks/aws/rhc-auth-store-policy.ts:5` and `stacks/aws/transcript-store.ts:93`, which has no leading dot and belongs to the RHC auth store.

## 1. Keys

### Grammar

```
prefix  = keyRoot "/.upload-inbox/" org "/v1/ws=" ws "/u=" uh "/"
key     = prefix "o=" originId "/b=" b32 "/d=" d32 "-w" seq ".json.zst"

keyRoot = [a-z0-9][a-z0-9-]{0,62}              ; "96bulls" hosted; self-host: its INGEST_KEY_ROOT
org, ws, originId = segment
segment = [A-Za-z0-9._-]{1,128}, not starting with "."
uh      = first 32 hex of sha256( JSON.stringify(["admission-user-v1", ws, user]) )
b32     = first 32 hex of sha256( UTF-8 bytes of batch_id )
d32     = first 32 hex of sha256( the exact stored object bytes, i.e. the zstd frame )
seq     = "0" | [1-9][0-9]{0,15}, a safe integer equal to the witness "seq"
hex     = lowercase
```

- **The segment rule** is `writer.ts` `assertTenantSegment` (`src/session-ingest/writer.ts:144-148`). The key-root rule is that function's too. The self-host `INGEST_KEY_ROOT` check (`src/session-ingest/selfhost-config.ts:266`) is looser, but every admission already passes `assertTenantSegment`, so the effective rule is the stricter one. A test compares the module's segment rule with `assertTenantSegment`, input by input.
- **The leading dot** keeps `.upload-inbox` disjoint from every tenant prefix `<keyRoot>/<org>/`, for the same reason as `INBOX_NAMESPACE = ".admission-inbox"` (`src/session-ingest/async-admission.ts:75-80`).
- **`uh` is the privacy journal's machine segment without its `srv_` prefix.** The derivation is byte for byte the one in `async-admission.ts` `userDir` (`:124-125`, used by `journalKey` at `:127-129`). It hashes the raw workspace id and user id with `JSON.stringify`, not canonical JSON. For any `ws` that satisfies the segment rule, `layoutComponent(ws) === ws`, so the `ws=` segment also matches the admission inbox's `ws=` segment.
- **The builders refuse non-segment input rather than mapping it.** The admission inbox maps `ws` through `layoutComponent`; this contract does not.
- **Keys are content-addressed.** Each key is unique per (tenant, origin, batch, exact bytes, witness seq), and the PUT is create-only (`If-None-Match: *`). A retry of the same bytes under the same witness hits the same key and gets 412, which means "already queued". A batch re-sent under a new witness or with different bytes gets a new key. The claim still dedupes by batch id and digest, as for the admission inbox (`async-admission.ts:118-119`).

| function (module)                                   | produces                                                                                                            |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `userSegment(ws, user)`                             | `uh` (vector `userSegment.uh`; `userSegment.journalKey` shows the same hash in the journal key)                       |
| `uploadKeyPrefix({keyRoot, orgId, workspaceId, userId})` | `keyPrefix` (vector `keyPrefix`)                                                                                    |
| `uploadObjectKey(prefix, {originId, batchId, objectSha256Hex, witnessSeq})` | the object key (vector `objectKey`)                                                                     |
| `parseUploadKey(key)`                               | the parts (vector `parsedKey`) or `{code: "upload_key_invalid"}`. The caller compares `keyRoot` with its own.         |
| `parseUploadKeyPrefix(prefix)`                      | prefix parts, or null                                                                                               |
| `batchSegment(batchId)`, `uploadObjectSha256Hex(bytes)` | `b=` and the full digest whose first 32 hex chars are `d=` (vector `object`)                                    |

## 2. The object

- **Body:** exactly one zstd frame. Inside is the UTF-8 JSON delivery request, exactly as it would be sent to `POST /v1/delivery/batches`: `{"protocolVersion":1,"batch":{schema_version, origin_id, batch_id, job_id, generation, destination_id, instance_id, account_id, mapping_version, records}}` (`parseDeliveryRequest`, `src/session-ingest/vendor/delivery/prepare.ts:355-358`).
- **Size:** at most `MAX_DELIVERY_BYTES` = 2 097 152 stored bytes, measured before decoding (`src/session-ingest/vendor/delivery/delivery-contracts.ts:115`). After decoding, the usual delivery limits apply, as in `boundedJson` (`src/session-ingest/app.ts:244-273`): decoded size at most `MAX_DELIVERY_BYTES` and at most `MAX_DELIVERY_RECORDS` records.
- **PUT headers:**

| header                                   | value                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `If-None-Match`                          | `*` (create-only)                                                                                             |
| `Content-Type`                           | `application/json`                                                                                            |
| `Content-Encoding`                       | `zstd`                                                                                                        |
| `x-amz-checksum-sha256`                  | base64 (standard, padded) of the raw sha256 of the stored bytes (`uploadChecksumSha256`; vector `object.checksumSha256Header`) |
| `x-amz-server-side-encryption`           | `aws:kms`                                                                                                     |
| `x-amz-server-side-encryption-aws-kms-key-id` | the credentials response's `kmsKeyId`                                                                    |
| `x-amz-meta-relay-witness`               | the witness token, verbatim                                                                                   |

- **Responses:** the desktop treats **200 or 412** as "Queued" and then polls §5. Any other answer leaves the batch in the desktop's queue for a retry. That retry uses the same key while the witness is unchanged.
- **Consumer checks:** `account_id` must equal `deliveryAccount(org, ws)` = `"relayhistory:" + sha256hex(canonicalJson([org, ws]))` (`prepare.ts:549-551`; vector `deliveryAccount`, computed with the vendored function itself). `batch.origin_id` must equal the key's `o=`.

## 3. The witness

```
token   = "v1." payloadB64url "." macB64url               ; ASCII, at most 1024 bytes
payload = {"v":1,"org":"<org>","ws":"<ws>","user":"<user>","seq":<int>,"exp":<int>}
mac     = HMAC-SHA256(key, "relay-upload-witness-v1\n" + payloadB64url)
```

- **Payload:** exactly these six keys, in exactly this order, and nothing else. It must be the exact `JSON.stringify` serialization: no whitespace, no escapes that `JSON.stringify` would not produce. `seq` is the user's privacy-journal seq at mint time (`async-admission.ts`, the journal behind `journalKey`). `exp` is in unix seconds. `org` and `ws` are segments. `user` is 1 to 512 UTF-8 bytes with no control characters.
- **Base64url:** unpadded and canonical. A text that does not re-encode to itself is refused, which covers padding and non-zero trailing bits. The MAC is exactly 32 bytes.
- **Key:** the `UPLOAD_WITNESS_KEY` setting, shared by control and the consumer. It is 32 random bytes encoded as unpadded base64url. `parseUploadWitnessKey(value)` refuses any other length or encoding by **throwing**. A misconfigured consumer must retry rather than write terminal refusals. The key lives in 1Password and the platform secret store, never on disk.
- **Verification** (`verifyUploadWitness(key, token, nowSeconds)`):
  1. Check the form.
  2. Compare the MAC in **constant time** (`timingSafeEqual`), before the payload is parsed.
  3. Check that the payload is in its exact form.
  4. Check expiry: `exp <= nowSeconds` (the consumer's clock) means `upload_witness_expired`.
  It returns the payload or `{code}`. This matches the repo's HMAC habit (`app.ts:77-82` signs `v1\n…`; `app.ts:96` compares in constant time).
- **Stale witnesses refuse, never admit wrongly.** If `seq` is behind the journal at admission time, the upload is refused with `delivery_privacy_superseded`, by the existing post-claim gate `assertNoLaterPrivacyControl` (`async-admission.ts:421-434`). If `seq` is ahead of the journal, it is refused with `upload_witness_seq_mismatch`.
- `encodeUploadWitness(key, payload)` is control's side. `readUploadWitnessUnverified(token)` lets the desktop self-check a credentials response. It never authorizes anything.
- **Vectors:** `witness.token` was produced by `encodeUploadWitness` with `witness.testOnlyKey` and verified at `witness.verifiedAtSeconds`. `witness.macInput` is the exact HMAC input.

## 4. Credentials (`POST /api/v1/workspaces/{ws}/relayhistory/upload-credentials`, relay-control)

**Request:** `{"originId": "<segment>", "kind": "sts" | "presigned", "keys"?: ["<key relative to keyPrefix>", …]}`. `keys` is used for `presigned` only.

**Answers:**

- **200:** one of the two bodies below.
- **404:** the feature is off for this caller (`HISTORY_UPLOAD_DIRECT`). The desktop falls back to the HTTP POST path.
- **403:** authentication or authorization refusal.

```
STS:       {"contract":"relay-upload-inbox-v1","kind":"sts","bucket","region","endpoint":null,"keyPrefix","kmsKeyId",
            "credentials":{"accessKeyId","secretAccessKey","sessionToken","expiresAt"},
            "witness","witnessSeq","maxObjectBytes":2097152,"refreshAfter"}
presigned: {"contract":"relay-upload-inbox-v1","kind":"presigned","bucket","region","endpoint":null,"keyPrefix","kmsKeyId",
            "maxObjectBytes":2097152,"refreshAfter","witness","witnessSeq","urls":[{"key","url","expiresAt"}]}
```

`parseUploadCredentialsResponse(value)` validates these bodies, with exact keys at every level, and returns the typed body or null. The vectors `credentials.sts` and `credentials.presigned` pass it. It checks the following:

- **Timestamps:** `expiresAt`, `refreshAfter` and each url's `expiresAt` are RFC 3339 UTC strings ending in `Z` and naming a real instant. `refreshAfter` is not later than the earliest expiry in the body.
- **`maxObjectBytes`** equals `MAX_DELIVERY_BYTES`.
- **`keyPrefix`** parses as a §1 prefix.
- **The witness matches the prefix.** Its payload, read unverified, has the `keyPrefix` tenant: the same org and ws, and `userSegment(ws, user)` equal to `u=`. Its `seq` equals `witnessSeq`.
- **Presigned urls:** 1 to 100 entries with distinct keys. Each `key` is relative to `keyPrefix`, and `keyPrefix + key` parses as a §1 key with `w<witnessSeq>`. Each `url` is an absolute http(s) URL with no userinfo and no fragment.
- **`endpoint`** is `null` (the provider's default endpoint for `region`, which is what hosted always sends) or an http(s) origin URL with path `/`, for a self-host S3-compatible store.
- **`bucket`** follows S3 bucket naming. **`region`** is `[a-z0-9-]{1,64}`. **`kmsKeyId`** is a non-empty printable string.

Credentials are secrets in transit. They are never logged or persisted beyond the desktop's in-memory use.

## 5. Admission status (`GET /v1/delivery/admission?uploadKey=<url-encoded key>`, this pipeline)

The existing `originId` + `receiptId` form of the same route stays unchanged (`app.ts:869-879`).

**200:**

```
{"contract":"relay-upload-inbox-v1","uploadKey","state":"pending"|"admitted"|"refused",
 "code"?, "receiptId"?, "receivedAtMs"?, "decidedAtMs"?, "retryAfterSeconds"?}
```

| field               | rule                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `state` | one of `UPLOAD_ADMISSION_STATES` = `pending`, `admitted`, `refused` |
| `code` | present exactly when `refused`; one of the §6 codes |
| `receiptId`         | `rhr_<64 hex>`, only on `admitted` or `refused`, when known                                 |
| `receivedAtMs`      | non-negative integer, any state                                                            |
| `decidedAtMs`       | non-negative integer, terminal states only                                                 |
| `retryAfterSeconds` | integer 1 to 3600, `pending` only. The server also sends a `Retry-After` header on pending. |

**Errors** (`UPLOAD_STATUS_HTTP_ERRORS`):

| status | code                     | meaning                                                                    |
| ------ | ------------------------ | -------------------------------------------------------------------------- |
| 400    | `invalid_delivery`       | the key does not parse                                                     |
| 403    | `upload_tenant_mismatch` | the key's (org, ws, uh) is not the caller's identity                       |
| 404    | `upload_unknown`         | neither the object, nor its tombstone, nor an outcome exists               |
| 503    | `delivery_unavailable`   | store failure; sent with `Retry-After` (as `IngestUnavailable`, `src/session-ingest/deliver.ts:178-181`) |

The desktop stops polling on 404 and on a terminal state. `parseUploadAdmissionStatus(value)` validates the 200 body with exact keys. The vectors `admissionStatus.pending`, `.admitted` and `.refused` pass it.

## 6. Refusal codes (`UPLOAD_REFUSAL_CODES`, closed)

The consumer applies these checks in this order. The first failure is the upload's terminal refused outcome. Retryable conditions are never refusals: store or queue failures, `privacy_control_pending` (`async-admission.ts:437-439`), and a misconfigured key.

| code | check / meaning |
| --- | --- |
| `upload_key_invalid` | the key does not parse under §1 (`parseUploadKey`) |
| `upload_witness_invalid` | `x-amz-meta-relay-witness` missing or malformed, not the exact payload form, or the MAC does not verify |
| `upload_witness_expired` | witness `exp` is at or before the consumer's clock |
| `upload_tenant_mismatch` | key (org, ws, uh) differs from the witness (org, ws, `userSegment(ws, user)`) (`bindUploadToWitness`) |
| `upload_witness_seq_mismatch` | key `w<seq>` differs from the witness `seq`, or that seq is ahead of the user's journal |
| `delivery_too_large` | stored object over `MAX_DELIVERY_BYTES` (`checkUploadObjectBytes`), or decoded/prepared delivery over its limits |
| `upload_digest_mismatch` | `d=` is not the sha256 of the stored bytes (`checkUploadObjectBytes`) |
| `unsupported_encoding` | the object is not one zstd frame |
| `invalid_delivery` | not UTF-8 JSON, or not a valid delivery request |
| `unsupported_protocol` | `parseDeliveryRequest`: `protocolVersion` is not 1 |
| `unsupported_schema` | `parseDeliveryRequest`: batch or record `schema_version` unsupported |
| `unsupported_mapping` | `parseDeliveryRequest`: `mapping_version` unsupported |
| `unsupported_evidence` | `parseDeliveryRequest`: a record's evidence kind is unsupported |
| `delivery_account_mismatch` | `batch.account_id` is not `deliveryAccount(org, ws)` |
| `upload_origin_mismatch` | `batch.origin_id` differs from the key's `o=` |
| `delivery_budget_exceeded` | the batch exceeds the destination's per-request budget (`assertWithinBudget`, `deliver.ts:145`) |
| `delivery_privacy_superseded` | a reset or re-enable completed after the witnessed journal seq (`assertNoLaterPrivacyControl`) |
| `admission_invalid` | the admission inbox object or receipt failed its own checks (`AdmissionRefused`, `async-admission.ts:97-101`) |
| `admission_failed` | admission failed for a reason with no narrower code |
| `tenant_not_a_segment` | the org is not a valid key segment for this key root (`assertTenantSegment`) |

The `parseDeliveryRequest` codes come from the vendored `prepare.ts` (`:47`, `:238`, `:258`, `:277`, `:306`, `:315`). `delivery_account_mismatch` comes from `prepare.ts:558`.

**Refusal vectors** (`refusals`): each entry names the module function (`fn`), its input, and the code it returned. They cover:

- a key with the wrong suffix and a key with a dot-leading org (`parseUploadKey`);
- a tampered MAC and an expired witness (`verifyUploadWitness`);
- a witness for another user and a witness with another seq (`bindUploadToWitness`);
- bytes whose digest is not `d=` (`checkUploadObjectBytes`).

## 7. What this contract does not change

- **No existing code changes:** this pipeline's routes, the async-admission inbox, the consumer's key-prefix check (`admission-consumer.ts:73`), the IAM grants and the bucket notifications are unchanged.
- **Wiring later:** the consumer that admits upload-inbox objects, the status route's `uploadKey` form, and every AWS resource arrive in later PRs. Each AWS action needs its own approval (decision 0004).
