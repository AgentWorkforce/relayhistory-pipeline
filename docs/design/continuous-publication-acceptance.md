# Continuous publication acceptance

Use a disposable PostgreSQL database and versioned object store with synthetic identities. These cases specify the acceptance boundary for backlog-to-tail handoff and a future hosted canary; executing the local suite does not demonstrate production coverage. Pin the implementation, migrations, image, target generation and source contract revision in the receipt.

## Catch-up and tail

Use two organizations, two workspaces, two origins per active user, a hot origin, a quiet origin and a separate caller lacking access. Seed accepted stages with overlapping revisions, a superseded stage, an unacknowledged stage object and equal timestamps. Create an independent oracle from acceptance/authority records and source ordering. Compare sets by complete identity, including revision, rather than total counts alone.

1. Capture the baseline, start catch-up, and accept new stages before scan, during claim, after page boundary and immediately before the terminal empty page. Rerun with a lower-sorting key inserted behind the cursor. Every eligible arrival must reach the oracle or remain explicitly pending for a subsequent scan. A successful empty cycle alone cannot establish catch-up.
2. For any cohort already processed by the separate drain, test handoff under a proposed exclusion or equivalent idempotency protocol. Live SQL-buffered cohorts keep HTTP admission open and require no one-off drain. Interrupt the handoff on both sides. Verify the same accepted stage produces one logical active head, skipped stages retain durable reasons, and already-drained data remains visible without duplicate index events. Hold rollout until the two paths have a proven common visibility model.
3. Advance an origin independently; present an expired or wrong-generation frontier and one for a different bucket, root, user or origin. Require refusal and a fresh authority decision on renewal. For an equal-revision conflict, retain evidence of losing candidates and confirm the source-authoritative winner. Keep superseded or unacknowledged objects out of canonical results.
4. Inject a reset, open privacy control, erase, ownership move or generation transition at selection, after claim, after object write, and immediately before commit. Force lease loss and concurrent reclaim at the same boundaries. Verify at the serialization point that stale work cannot install a visible head. Where commit wins first, verify the later ordered control fences reads and retires the artifact through the erasure lane. Recheck with the former owner and unrelated caller. Detached bytes must be unreachable and eventually accounted for by retirement.
5. Kill the process before write, after write but before commit, and after commit before acknowledgment. Restart with a fresh process and no cached cursor. Reconcile active head and bytes, immutable object versions, retired candidates, queue/index state and receipts. Simulate duplicate delivery and replay the same frontier evidence. Require idempotent recovery or a durable held reason with a repair owner.
6. Keep the hot origin saturated across multiple batches while the quiet origin submits a single eligible stage. Add a repeatedly failing origin and periodic generation changes. Record ticks and eligible wait time per origin in the synthetic harness; assert progress for each continuously eligible scope within the agreed scheduling bound. Repeat with a bounded batch size of one. Specify the numeric bound with the runtime owner before sign-off; a per-tick limit alone supplies no fairness guarantee.

## Same-caller end-to-end comparison

For each cohort session, record alias, canonical head/pointer presence, directory-row presence and index convergence. Use the same authorized caller, workspace, owner constraints, list/window filters and page traversal for canonical and hosted checks. Use a short, unique synthetic search term and a known event count. Check canonical directory/list integration, point events and indexed search against hosted History `GET /v1/sessions`, `GET /v1/sessions/:sessionId/events` and `GET /v1/events?q=…`; exercise the actual MCP list/point/search client when that is the reported path. A Reader point/list success via the owner-buffered projection does not establish canonical publication. Prove the serving backend from route telemetry or mark it unknown. A canonical-only success with a hosted miss goes to the History routing owner. Never infer a route from a 200 alone.

Run any production verification only within its approved scope. Keep cohort identities in the private receipt. Public results contain aliases, statuses, counts, observed backend and timestamps only. Capture denied and post-erasure results alongside positive cases; omit tokens, payloads, credentials and raw object paths.

## Operational evidence

At baseline and every observation window record accepted, newly eligible, published, previously published, deferred and excluded counts with their denominators and window; distinct sessions; oldest continuously eligible age; frontier age, expired scopes and validation refusals by reason; DB load and claim latency; commit retries; active versus retired bytes pending erasure; downstream index age; and rate of same-caller search/point/list mismatches. Report missing series explicitly. Reconcile unique identities over the whole run so retries cannot inflate throughput. Track oldest age and sustained progress while arrivals continue, throughout live admission. Agree alert thresholds, target catch-up lag, authorized read scope and cleanup SLA before promotion. Stop expansion on an unexplained mismatch, stale generation, confirmed starvation or failed retirement; pause the publisher while leaving privacy/erasure processing active.

Existing component evidence: `src/session-ingest/__tests__/{buffered-drain,publication-canary,publication-authority,frontier-plan}.test.ts`. These suites cover parts of the matrix. Continuous live arrivals across an entire handoff, fair service under sustained load, real hosted routing and downstream convergence require integration receipts.
