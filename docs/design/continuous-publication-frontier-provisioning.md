# Continuous publisher frontier provisioning decision

Reviewed base: `34f600588f8f87bdf6a662dae2ae2ec27f07fb16`. The pipeline lead owns the source integration. The source authority, independent evidence verifier, installation operator and on-call owner must each be identified before activation. Keep the publisher dormant during provisioning design.

## What can be reused

The [capture and planner](../canonical-frontier-plan.md) bind source maxima, verified immutable export bytes, privacy controls, physical destination, generation and finite bounds. The [receipt reader contract](frontier-producer-resumption-20261108.md) defines a bounded client for a separately installed, restricted RPC. The [attester vectors](../contracts/frontier-attester-20261107/) pin byte encodings and ordering. Current capture deliberately returns a hold when receipt closure is absent. Fixtures in the two publication proof scripts insert synthetic frontier rows; they cannot supply source evidence for provisioning.

## Implementation and review sequence

1. **Qualify the read boundary.** Implement the receipt profile and restricted RPC from the receipt reader contract. Bind one authenticated source role, one org/workspace/user/origin, active schema generation, exact destination and authority, profile expiry and work budget. Verify the installed owner and function definition independently on each supported PostgreSQL major. Capture all native, retained and superseded candidates required by the receipt domain, including equal-revision losing candidates. Completeness requires a terminal empty page, exact count/digest and a fresh closing read. Refuse on gaps, mixed generations, digest drift or insufficient visibility.
2. **Prepare a plan with replayable evidence.** Capture source maxima, ordered controls, reset and erasure state and versioned export evidence before and after the receipt scan. Recompute all evidence digests and verify the exact scope, target and generation with the independent verifier. Require whole-user coverage wherever privacy control scope spans multiple origins. Persist the candidate plan and verdict under the existing content-addressed plan contract with custody appropriate for tenant evidence. Separate the capture identity from the installer. The publisher cannot extend a plan or write frontier rows.
3. **Install and renew through one guarded transaction.** The proposed owner-only RPC must admit the exact approved plan bytes and authenticated installer, compare current authority and predecessor under the same locks used by scoped claim/control, verify the admission has not been consumed differently, and atomically record the admission, audit outcome and per-origin frontier. An exact replay returns the prior outcome. Stale, expired or conflicting evidence requires recapture. Never refresh an expiry by copying a prior digest. Keep public timestamps and receipts free of identifying data. Restrict raw plan custody to approved roles.
4. **Fence runtime use and retirement.** Bind scoped candidate acquisition and final publication to the admitted plan, current authority and target. Test changes to generation, privacy head, reset, source lineage, schema and ownership between selection, claim and commit. Refuse stale claims and leave retirement/erasure processing active during pause. Report capture age, held origins by reason, frontier expiry, oldest eligible pending and post-index verification in aggregate.
5. **Reserve actual migration identifiers with the current registry.** Historical design names 049000/050000 identify contracts only. Main already contains the operator erase migration at 20261105050000 and later ledger entries. An implementation needs fresh ordered slots, per-major SQL review and adoption/rollback tests before any release plan. A migration or scope change must go through its own approval.

## Decision gates

The schema owner must settle the complete receipt-domain query, supported-work bounds and authoritative profile lifecycle. The privacy/source owner must qualify inputs and invalidation paths. The verifier and installer owners must prove concurrent reset/erase, changed generation, crash/retry and forged/stale plans on isolated PG15/16/17 with synthetic S3 inputs. A scoped canary must connect the resulting manifest to canonical and hosted visibility; an S3 marker alone cannot establish that. No source path that invents a frontier or treats an empty input as completeness can qualify.

This design does not change the one-off S3 backlog workflow. Its export/fence receipts have a different domain and do not authorize continuous frontier installation.

## Local catch-up and tail scheduler proposal

The current `ingest_publication_candidates` RPC in `20261104060000_ingest_canonical_publication.sql` already scans current buffered/acknowledged/live rows with a matching unexpired frontier each tick, ordered oldest first. It has no durable watermark. It cannot report why missing frontiers held otherwise buffered receipts. A continuously busy older cohort can delay new receipts.

`src/session-ingest/publication-reconciliation.ts` is a separately tested scheduling component for a future scoped inventory adapter. It has no runtime binding, database grants, frontier writer or completion ledger. Per authorized scope it alternates a bounded catch-up page, whose upper bound stays fixed until explicit EOF, with a bounded forward tail page above the initial high key. A later sweep revisits rows committed behind either cursor and retries prior holds. A pass through retained inventory costs O(inventory); under sustained load use an indexed keyset and measure old-sweep age, tail age, hold counts and retry backlog. Progress assumes finite work ahead and successful ticks. A per-scope scheduler alone cannot guarantee fleet-wide fairness.

Integration requires an immutable-position inventory and independently qualified scoped claim/commit adapter, a durable scope/generation-bound cursor store with compare-and-swap, and bounded per-org scheduling with error backoff. The position is an outbox timestamp and stage-token tiebreaker; if the active stage changes behind a cursor the next sweep must rediscover its replacement. The inventory must return only the assigned scope and must never substitute its observations for claim-time privacy and authority checks. Normalize terminal outcomes from authoritative receipts, not attempts; the returned counts are per-visit operational outcomes and cannot be summed into a unique-backlog total. Retry a failed page at the same checkpoint; partial effects require idempotent claim/commit and re-read on replay. A raw `highest()` result never proves absence, eligibility or publication. Add scoped Postgres concurrency, index/budget and MinIO crash/replay qualification before wiring this component to any deployment.

## Guarded installation boundary

`src/session-ingest/frontier-install.ts` is an unwired one-shot caller for the v3 installation ceremony. Its sole public operation recomputes the existing planner result over capture and verified immutable export bindings and compares it to the plan named by an independently loaded approval. The command contains exactly one origin row, the predecessor hash (null means exact absence), the approval nonce, the independently approved verifier/whole-user commitments and the planner capture/evidence digests. A mismatched receipt, stale capture, insufficient 150-second window or incomplete capture cannot reach the installer. An uncertain write returns `audit_lookup_required`; query the exact committed nonce and command digest before any operator recovery.

The two injected capabilities are security boundaries. The approval reader must authenticate the verifier and reviewer and obtain the unconsumed approval from the independent ledger. Hashes supplied by a caller cannot implement that capability. The atomic destination RPC must recheck eligibility under the existing privacy/ownership locks, compare the exact approved predecessor and proposed row, enforce strictly increasing expiry on renewal, prevent ABA/replay, reject live leases and consume the nonce with append-only audit in the same transaction. A response digest alone authenticates nothing without this qualified RPC and its authenticated connection. Neither capability is available in the production runtime. The local tests verify translation, rejection, and ambiguous-outcome behavior using synthetic ports; live installation requires the independently qualified source proof, approval ledger and transactional RPC described above.

### Durable retry scheduling contract

`runPublicationRetryTurn` preserves the original page API. The caller supplies an authenticated source and durable store bound to the digest of the exact tenant, generation and physical target. Each scan turn alternates with a retry turn; scan turns retain the historical/tail rotation. The shared page budget is 1–20 visits per turn. A typed recoverable failure defers that token while the remainder of the page proceeds. The six-attempt limit counts the first visit; waits start at five seconds and double up to sixty seconds. Exhaustion and unclassified/ambiguous outcomes become durable holds requiring independent operator reconciliation. Retained retry records contain token, attempt count, state and due time only. Revisiting inventory cannot bypass a deferred or held record.

The adapter must CAS every token mutation and the scope checkpoint in one transaction. On thrown/ambiguous commit, reload durable state; never advance a cached checkpoint. Claims/commits must remain idempotent and revalidate current authority even if a crash or conflicting scheduler replays the page before its retry record was persisted. Scheduling rows cannot establish publication or authorize a retry of an ambiguous write. The disposable SQLite fixture exercises restart and rollback. A production persistence adapter, an indexed due scan, store retention/operator resolution and qualification against actual claim receipts are still required.

### Receipt-domain qualification while traffic continues

At the reviewed base, the only catalog reference to `ingest_scoped_publication_receipt_capture_v1(jsonb)` in the capture path is the proposed RPC client. The existing `ingest_receipt_seats_for_stage(uuid)` in `20261104055000_lazy_current_custody.sql` reconstructs seats for a **specified stage**. It cannot prove the independently complete receipt domain for an origin. `composeCanonicalFrontierCapture` in `frontier-capture-source.ts` intentionally leaves receipt decisions empty and omits that scan. A complete legacy inventory/export cannot close that gap.

The restricted client now compares **every** observed receipt page including explicit EOF in two distinct repeatable-read transactions. It verifies the installed function and reader identity in both transactions, compares actual page hashes and the authority/count/digest, and refuses if even a losing candidate changes. Each pass is bounded by the same opening page count; the existing byte and elapsed-time budgets cover both combined. This may cause additional conservative holds for large origins. Two identical snapshots of an incomplete SQL join could still agree. The client cannot establish source completeness or close the race after its final snapshot.

The pipeline schema owner must deliver the reviewed restricted RPC/profile with an independently bounded enumeration of native/current and losing receipt candidates, original admission/claim/stage ownership, current reset lineage and missing-join diagnostics. Decide the exact ordered migration slot with the schema registry and freeze the function-definition digest and owner **per supported PostgreSQL build**. Before integrating the client into capture, prove on disposable PostgreSQL that late commits, equal-revision contention, native-only rows, erased/reset origins and disappearing joins either reconcile in full or hold. Authorization of an individual live window still requires independent verifier/reviewer coverage of the whole user and a final under-lock authority/CAS recheck. For high-write scopes that cannot complete the two captures within the finite window, retain the hold pending an independently approved snapshot/barrier protocol.

### Disposable lifecycle evidence

The PGlite rehearsal in `frontier-plan.test.ts` exercises the actual TypeScript installer with a transaction-local PostgreSQL fixture and separately stored synthetic approvals. It verifies rollback of the frontier, nonce and audit on an injected precommit fault; audit lookup after a lost acknowledgement; rejection of a consumed nonce; pause without expiry extension; explicit control-path invalidation; refusal during live lease, generation mismatch and predecessor race; and recovery only after fresh approval for the current image. The fixture uses a single synthetic origin and one PostgreSQL connection. It does not qualify production roles, the independent verifier, real multi-connection lock ordering or the receipt-domain query. Those require the actual reviewed migration and provider proofs. No fixture SQL belongs in production migrations.

### Source-bound scoped claim and finalization rehearsal

The three proposed `sessions.ingest_publication_scoped_{candidates,claim,publish}_v1(jsonb)` functions live solely in the disposable `publication-scoped-v1.sql` fixture. Each receives the ordinary generation and inputs plus a `binding` containing `planSha256`, `admissionId`, `frontierSha256`, exact four-field tenant and five-field physical target. Publish additionally requires the stage token. Candidate limit is one, and the reviewed fixture admission enumerates exactly one stage. Discovery is a hint; claim and finalize reacquire the user fence, lock and re-read the independent admission, and compare current authority and target before delegating to the ordinary claim/publish checks. A successful claim records its attempt/lease atomically. An uncertain final response can be retried with the identical binding, ticket and messages while authority still holds. After invalidation, look up the audited outcome separately. Lost-claim or expired-lease ambiguity holds the occupied one-shot admission for audited reconciliation; automatic reclamation has not been qualified.

The fixture starts with synthetic trusted admission rows. It neither authenticates origin completeness nor creates real approvals. It revokes the ordinary claim/publish functions from the fixture ingest role to detect accidental fallback. Production requires an independently qualified **dedicated scoped execution identity**, provider-specific grants and proof that existing ingest, backlog and erasure roles retain their normal privileges. Do not copy the fixture REVOKEs to any deployment. Real PG15/16/17 two-connection tests must prove lock compatibility with control, GC, directory and invalidation paths. PGlite proves transaction ordering and rollback only on a single backend. The independently approved active stage set, expiry, per-executor identity, authoritative invalidation hooks, source RPC/profile and SQL role boundary remain production prerequisites.
