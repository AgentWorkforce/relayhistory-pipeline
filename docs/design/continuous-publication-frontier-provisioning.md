# Continuous publisher frontier provisioning decision

Reviewed base: `34f600588f8f87bdf6a662dae2ae2ec27f07fb16`. The pipeline lead owns the source integration. The source authority, independent evidence verifier, installation operator and on-call owner must each be identified before activation. Keep the publisher dormant during provisioning design.

## What can be reused

The [capture and planner](../canonical-frontier-plan.md) bind source maxima, verified immutable export bytes, privacy controls, physical destination, generation and finite bounds. The [receipt reader contract](frontier-producer-resumption-20261108.md) defines a bounded client for a separately installed, restricted RPC. The [attester vectors](../contracts/frontier-attester-20261107/) pin byte encodings and ordering. Current capture deliberately returns a hold when receipt closure is absent. Fixtures in the two publication proof scripts insert synthetic frontier rows; they cannot supply source evidence for provisioning.

## Implementation and review sequence

1. **Qualify the read boundary.** Implement the receipt profile and restricted RPC from the receipt reader contract. Bind one authenticated source role, one org/workspace/user/origin, active schema generation, exact destination and authority, profile expiry and work budget. Verify the installed owner and function definition independently on each supported PostgreSQL major. Capture all native, retained and superseded candidates required by the receipt domain, including equal-revision losing candidates. Completeness requires a terminal empty page, exact count/digest and a fresh closing read. Refuse on gaps, mixed generations, digest drift or insufficient visibility.
2. **Prepare a plan with replayable evidence.** Capture source maxima, ordered controls, reset and erasure state and versioned export evidence before and after the receipt scan. Recompute all evidence digests and verify the exact scope, target and generation with the independent verifier. Require whole-user coverage wherever privacy control scope spans multiple origins. Persist the candidate plan and verdict under the existing content-addressed plan contract with custody appropriate for tenant evidence. Separate the capture identity from the installer. The publisher cannot extend a plan or write frontier rows.
3. **Install and renew through one guarded transaction.** The proposed owner-only RPC must admit the exact approved plan bytes and authenticated installer, compare current authority and predecessor under the same locks used by scoped claim/control, verify the admission has not been consumed differently, and atomically record the admission, audit outcome and per-origin frontier. An exact replay returns the prior outcome. Stale, expired or conflicting evidence requires recapture. Never refresh an expiry by copying a prior digest. Keep public timestamps and receipts free of identifying data. Restrict raw plan custody to approved roles.
4. **Fence runtime use and retirement.** Bind scoped candidate acquisition and final publication to the admitted plan, current authority and target. Test changes to generation, privacy head, reset, source lineage, schema and ownership between selection, claim and commit. Refuse stale claims and leave retirement/erasure processing active during pause. Report capture age, held origins by reason, frontier expiry, oldest eligible pending and post-index verification in aggregate.
5. **Reserve actual migration identifiers with the current registry.** Historical design names 049000/050000 identify contracts only. Main already contains the operator erase migration at 20261105050000 and later ledger entries. An implementation needs fresh ordered slots, per-major SQL review and adoption/rollback tests before any release plan. A migration or scope change must go through its own approval.

## Decision gates

The schema owner must settle the complete receipt-domain query, supported-work bounds and authoritative profile lifecycle. The privacy/source owner must qualify inputs and invalidation paths. The verifier and installer owners must prove concurrent reset/erase, changed generation, crash/retry and forged/stale plans on isolated PG15/16/17 with synthetic S3 inputs. A scoped canary must connect the resulting manifest to canonical and hosted visibility; an S3 marker alone cannot establish that. No source path that invents a frontier or treats an empty input as completeness can qualify.

This design does not change the one-off S3 backlog workflow. Its export/fence receipts have a different domain and do not authorize continuous frontier installation.
