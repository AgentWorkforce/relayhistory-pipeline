# Large canonical scope execution prerequisite

Status: proposed execution and routing contract; no resource, permission, queue, flag, or production schema has been changed. The 256MiB producer is deliberately bounded and cannot serve all known sources. This plan does not certify a 64GiB worker as sufficient before measurement.

## Why a separate Node execution path

The operator's 2026-11-03 source catalog identifies 21 canonical cohorts above 256MiB; the largest physical manifest uncompressed chunk total is 1530237909 bytes and its complete cohort is 1530892459 bytes. `manifest.raw.raw_bytes` equals the sum of uncompressed chunk bytes; pointer `raw_bytes` copies that value. Actual records may cost more memory than source bytes, and a full union can include overlapping physical exports. The actual 187578412-byte combined synthetic run peaked at 3181887488 RSS including PGlite and the recorder. Neither the present Lambda allocation nor the 256MiB source ceiling establishes tail coverage.

A separate Node worker can reuse the authoritative fold unchanged. Increasing workerd input bounds would still require downloading the whole source in a 128MiB isolate and is excluded. A streaming rewrite is possible later, but it must retain full-union revision/accepted-sequence/tombstone/owner-domain semantics and external sorting; streaming raw lines alone does not solve that semantic problem.

## Selected proposed job contract

Use one canonical scope per isolated Node24 process in an existing GKE environment. Initial resource request for a capacity experiment: 8 CPU, 64GiB memory, 64GiB ephemeral disk, Node old-space ceiling 48GiB, one active scope per pod, 30-minute job deadline. These are requested experiment resources, not measured guarantees or claims about existing node-pool capacity. A job profile permits at most 2GiB uncompressed source bytes, 2M actual source records, 10000 pointers, 4M projected rows, and 16GiB unique artifact bytes. Every Worker-visible root/node/page remains <=256KiB, every segment <=64KiB, depth/fanout/version/hash semantics unchanged. Sources above any ceiling refuse and remain unready.

The source selector is the exact canonical org/workspace/harness/session identity plus current monotonic replay epoch. Capture still includes all live pointers, owners, revisions, raw digests, pending epochs and live directory authority. The worker runs the same shared projection, complete ClickHouse reconciliation and #171 metadata acknowledgement before artifact publication. It must not substitute last-writer-wins, truncate pointers, or reuse an old capture merely because raw bytes match. The existing final publication CAS remains authoritative after all immutable writes and read-back verification.

## Reliable handoff and recovery

An additive backend-only SQL job ledger is preferable to an unacknowledged CLI handoff. A unique canonical identity/current-epoch job is enqueued durably before the Lambda acknowledges oversized source work. Duplicate delivery converges to the same job. Jobs contain identifiers and source fingerprints, never raw payloads or credentials. Backend RPCs enqueue, claim with a random lease nonce and expiry, heartbeat, and finish only while the nonce and epoch still match. No new direct table grants are required. Claims use SKIP LOCKED and a bounded batch of one. Stale leases become claimable; a newer source epoch supersedes old queued/running work. A final publication failure or directory deletion never produces success. The ledger records a bounded error code and retry schedule; no error text containing source content.

Lambda routing is explicit and default off. It estimates complete union bytes from live pointer metadata before full hydration. A routing estimate is only a lower-bound selector: the worker independently validates actual manifest/chunk/record budgets. If handoff is enabled, failure to persist the job fails the source event for ordinary retry. Disabled handoff preserves refusal and unready metadata. A periodic backend reconciler discovers missing current publications and unfinished epochs, so a lost S3 notification or producer restart cannot permanently strand the cohort. Queue or ledger completion is separate from publication readiness.

## Runtime, permissions, and operator dependencies

A checked-in portable job entry point and dependency-injected runner should be built before infrastructure activation. The existing AWS Lambda bootstrap obtains Secrets Manager and S3 credentials from Lambda environment credentials; that bootstrap cannot be assumed to work in GKE. The deployment needs an explicitly reviewed identity federation or secret-provider binding, scoped S3 Get for current raw manifests/chunks and Put/Get for normalized read-projection keys, applicable KMS permissions, Supabase backend RPC access, and ClickHouse ingest access. No raw overwrite, Delete, old-version reads, new public table grants, or Neon write access is required. No credential values belong in a Job manifest or disk. Image digest, own-worktree install/build provenance, network egress, service account, resource availability, restarts, metrics, and termination grace period must be captured by the operator before enabling routing.

The repo's GCP deployment consumes published Helm charts. This lane must add a chart-owned worker/job definition through that source of truth rather than patch an opaque deployed chart or invent a second hand-maintained configuration. The exact worker image/entry point, job-ledger migration number, runtime credential provider and chart version are unreserved until implementation begins. No deployment or IAM grant is authorized by this plan.

## Required acceptance evidence

1. Generate a synthetic cohort at least as large as the known 1530892459-byte union, with a physical manifest totaling >=1530237909 uncompressed bytes across ordinary valid chunks, realistic record fields, multiple machines, tied microseconds, canonical aliases, tombstones, accepted-sequence/revision conflicts and large mandatory tool payloads. The actual largest chunk size is unknown; do not require one enormous JSON/string/chunk. Preserve source hashes and expected positions.
2. Run the actual Node producer plus actual #171 SQL and ClickHouse codec under the proposed process/container resource limit; measure RSS, old-space/external memory, wall time, CPU, artifact growth, object counts and largest object. A successful high-memory run does not prove the existing Lambda fits.
3. Run the real offline workerd consumer through bounded HTTP reads against the result. Assert first/continuation/boundary/middle/last identity/order/counters, full and maxContent reads, bounded object fetches, hash checks and final source acknowledgement.
4. Revert one fence at a time: old source ceiling must refuse the same corpus; deleting/recreating directory authority, owner/revision/raw-digest mutation, expired lease, superseding epoch, missing write/read-back object, corrupt index/page and source change during hydration must prevent success. Crash after object writes but before publication must retry idempotently; stale worker completion cannot overwrite a newer publication.
5. Verify queued oversize work survives Lambda retries, worker death and a missed source notification. Erasure must invalidate both the publication and pending work, and existing eraser/normalized-prefix cleanup must cover the new namespace before activation.

Until those checks and operator dependencies close, capacity remains red for the large-source tail and routing remains off. The analysis-cache prerequisite can be implemented independently; it does not close source-capacity readiness.
