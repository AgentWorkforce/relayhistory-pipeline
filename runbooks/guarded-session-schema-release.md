# Guarded production session-schema release (draft)

This is a manual GitHub Actions route, not an activation or a deployment. It uses the authoritative pipeline migrator. It never invokes Supabase CLI migration apply, Alchemy, or a Worker deployment. Apart from the migrator's own writes, its SQL writes are the CI event-trigger function refresh described under "Function boundary", built from the committed reviewed function body, and the separately approved **bootstrap** mode described under "Bootstrap stage", which creates only absent session roles from the committed reviewed bootstrap chain.

## Prerequisites and current blockers

An existing GitHub administrator must create **session-schema-production** before this workflow can run. Configure exactly one custom deployment branch policy (type branch, name main) with protected-branches deployment disabled. Where the repository plan supports required reviewers, configure directly named human User reviewers (Khaliq: User ID 1724137); Team-only reviewers are deliberately insufficient for the current approval verifier and refuse. Do not put credentials in a repository, file, artifact, command argument, GITHUB_ENV, or log. The workflow does not create the environment or configure any secret. Its GitHub token only reads Actions, deployments and repository contents; any inaccessible verification API fails closed.

The environment gate is checked before its name is emitted as the dependent job's environment output. The protected job then rechecks the gate and its human authority. When the environment has a required-reviewers rule, it requires an actual approved review-history entry for that environment ID by a presently configured human User reviewer, and any rejection recorded for that environment refuses; a reviewer rule never falls back to dispatcher identity. When the repository plan cannot create a reviewer rule (no required_reviewers protection rule exists), the human authority is the dispatch itself: both the run's actor and its triggering actor must be the pinned human User account (Khaliq, User ID 1724137). ### Function boundary: required control and CI refresh

There is no operator choice between function-boundary modes on this route. global-default-revoke is the required **pre-refresh control**: the catalog must already prove it at plan time and again under the migrator lock, and it is what the migration profile runs under. The reviewed sessions event trigger is refreshed and verified by CI itself, never selected by the operator:

- It must already exist with the exact safe identity recorded in the approved plan: ddl_command_end with the exact tag set, enabled ALWAYS; trigger, function and its private schema owned by the postgres migration owner; the reviewed plpgsql VOLATILE SECURITY INVOKER function returning event_trigger with the exact function configuration; EXECUTE for its owner only and none for PUBLIC; matching runtime-role setting.
- Under the migrator lock, CI refuses unless the committed wrapper source (supabase/bootstrap/hoopdb_sessions_function_boundary_supabase.sql) matches its pinned digest (release_boundary_wrapper) and the live trigger evidence still equals the plan's (release_boundary_changed). It then replaces that one function's definition (CREATE OR REPLACE with the committed body) in its own transaction and commits only if the full event-trigger evidence is then satisfied and the body digest is exact; otherwise it rolls back and refuses (for example release_boundary_refresh_unproven).
- The refresh never creates the trigger, transfers owners, changes ACLs or connects as another role. A missing trigger, a trigger owned by any role other than postgres, or any other identity drift refuses before the refresh.

No database URL is exposed to install/check-out/download/upload steps. Only the database invocation receives it. The connection has a ten-second connect bound, five-second lock timeout, five-minute statement timeout and one-minute idle-transaction timeout. Errors print fixed/sanitized codes, never driver message/detail/hint or connection URLs. Plan artifacts expire after one day. Concurrent runs serialize; an apply is not canceled by a second dispatch.

## Release anchor (held-step target_sha)

When a release holds steps, target_sha is never a generated worktree or an arbitrary main commit: it is the immutable tip of a protected branch `release/schema-<slot>` (src/hoopdb/schema-release-contract.ts releaseAnchorBranch). An upstream target `upstream:YYYYMMDDnnnnnn_name.sql` uses `release/schema-nnnnnn`; a history-lane target `96bulls:NNNN_name.sql` uses `release/schema-96bulls-NNNN`. A slot the release tree names twice (6-digit slots repeat across dates) cannot anchor. src/hoopdb/release-target.ts requireReleaseAnchor and releaseAnchorBinding check it from the local Git object database only; scripts/schema-release-github.ts checks the GitHub side. Plan, bootstrap and apply all recompute it before connecting, and apply recomputes it again under the migrator lock (beforeWrite).

**Ref.** The plan, bootstrap and apply jobs check out full history (fetch-depth: 0), which brings every branch in as `refs/remotes/origin/<branch>`. The exact ref `refs/remotes/origin/release/schema-<slot>` must exist and its tip must be the commit target_sha (a tag, a local branch or another namespace does not count). On GitHub the branch must exist, point at target_sha and be protected, and its own latest **push** ci and pg-proof runs (filtered to that branch) must be completed and successful at target_sha, with every job green. ci.yml and pg-proof.yml run on pushes to `release/schema-*` for this; an anchor on an older main base carries that trigger itself (see Workflow files below).

**Chain.** Each anchor commit has exactly one parent. Walking first parents from target_sha, every commit before main is the tip of a lower `release/schema-<slot>` anchor (strictly lower in migrator order), at most 64 levels; the first main commit reached (on the release sha's first-parent history) is the **main base**. target_sha itself must not be a main commit.

**Diff and bytes.** Every path that differs between the main base and target_sha must be on the anchor allowlist and byte-identical, mode included, to the release sha (absent at both counts as identical). The five bootstrap chain files must equal the release sha's bytes even when the anchor does not change them. The allowlist (src/hoopdb/release-target.ts RELEASE_ANCHOR_FIXED_PATHS, releaseAnchorPathAllowed):
- the bootstrap chain files (SESSION_BOOTSTRAP_FILES) and the seven phase 2 verifier files (RELEASE_TREE.verifiers);
- the function-boundary generator inputs scripts/sync-sessions-function-boundary.ts and scripts/sessions-function-boundary/{generate,sql,types,verifiers}.ts, and its lane modules scripts/sessions-function-boundary/lanes/*.ts;
- its generated outputs src/hoopdb/migrate-guards.ts, src/hoopdb/sessions-function-acl.json, supabase/bootstrap/hoopdb_sessions_function_boundary_supabase.sql and the eight supabase/bootstrap/*_verify.sql files;
- src/hoopdb/migration-sentinels.ts, src/hoopdb/session-bootstrap-chain.ts, src/hoopdb/session-bootstrap-roles.ts and src/hoopdb/session-bootstrap-consumers.ts;
- schema lane steps directly in supabase/migrations/*.sql and src/hoopdb/migrations/*.sql;
- supabase/rollbacks/<step>.down.sql only for an upstream step target_sha's tree carries.

Nothing else (tests, docs, runtime code outside that list) may differ from the main base.

**Workflow files.** A push runs the workflow files of the pushed tree, so an anchor whose main base predates 42797f3c (for example 113dc657, where ci.yml and pg-proof.yml run on `push: branches: [main]` only) gets no release/schema-* push run unless it carries the trigger itself. The anchor may therefore also change `.github/workflows/ci.yml` and `.github/workflows/pg-proof.yml`, and only as releaseAnchorWorkflowTransform (src/hoopdb/release-target.ts) of the main base's own bytes: the base must contain the line `    branches: [main]` exactly once, directly under `  push:` in the top-level `on:` block, and that one line is replaced by the three lines main's 42797f3c added:

```
    # release/schema-*: the protected release anchor branches (a held-step target_sha
    # needs green push runs on its own branch; scripts/schema-release-github.ts).
    branches: [main, 'release/schema-*']
```

Every other byte stays the main base's (jobs, permissions, actions, runners, paths, events, line endings). Both files must be mode 100644 at the main base and target_sha. These two files are compared with the main base, not the release sha. No other `.github/workflows/` file may differ. To build it, apply main's hunk: `git show 42797f3c -- .github/workflows/ci.yml .github/workflows/pg-proof.yml | git apply --index` on the main base (it applies cleanly to 113dc657 and yields exactly the transform). A main base that already runs on release/schema-* needs no workflow change; any change to its workflow files refuses.

**Prefix.** The release sha's own tree must prove the same ordered prefix through the target (every release step of the target's lane up to the target, the same names and sha256 in migrator order), and target_sha's tree must hold exactly that prefix with no step above the target in its lane (release_target_tail, release_target_tree_mismatch). The generation is the prefix plus target_sha's verifiers; phase 2 runs target_sha's verifiers from the object database and the PASS marker is written only for that generation. Held steps are never applied or ledgered.

**Refusal codes** (all fail closed before connecting, or before the first write under the lock):
- `release_anchor_ref_missing`: the target has no anchor branch name, the local ref is absent, or the GitHub branch does not exist.
- `release_anchor_ref_mismatch`: the anchor branch tip is not a commit or is not target_sha (locally or on GitHub; includes an anchor branch moved after the plan).
- `release_anchor_ref_unprotected`: the GitHub anchor branch is not protected.
- `release_anchor_ref_ambiguous`: the target's slot names no release step or more than one.
- `release_anchor_chain`: target_sha is a main commit, a parent is neither main nor a lower anchor tip, or the walk does not reach main.
- `release_anchor_nonlinear`: an anchor commit has zero or several parents.
- `release_anchor_extra_file`: the anchor changes a path outside the allowlist.
- `release_anchor_file_drift`: an anchor path (or a bootstrap chain file) differs from the release sha's bytes or mode.
- `release_anchor_workflow_drift`: the anchor changes ci.yml or pg-proof.yml to anything but the transform of the main base's bytes (including a copy from main, any other change, deletion or a mode other than 100644), the main base lacks the main-only push selector in its documented form, or the anchor changes any other `.github/workflows/` file.
- `release_anchor_prefix_mismatch`: the release sha's tree does not prove the prefix through the target.

Existing codes also apply: release_target_sha_unknown (unreadable or shallow history), release_target_verifier_missing, release_target_tail, release_target_tree_mismatch, release_target_ci and release_target_ci_jobs (anchor branch CI).

## Failure and rollback

A missing bootstrap (release_bootstrap_required: run the bootstrap stage), drifted bootstrap role (release_bootstrap_role_drift), a bootstrap chain file mixing target-required and above-target roles (release_bootstrap_chain_mixed), release chain bytes that differ from the anchor's (release_bootstrap_release_drift), a consumers manifest that does not cover the target (release_bootstrap_manifest), anchor contract modules that are partial, unparsable or differ from the release's (release_bootstrap_contract_drift), unsafe or wrong owner, unproven global control, missing or drifted event trigger, mixed Supabase CLI history, ledger gap/checksum drift, changed ledger since planning, stale source/CI, or missing human approval stops the route. Do not edit a ledger, suppress a verifier, disable TLS or switch credentials to continue. Obtain reviewed prerequisite work, re-run a new read-only plan, and approve the new exact generation.

The boundary refresh commits on its own before the PENDING readiness marker and the first migration; a later failure does not revert it (the refreshed body is the exact committed source). Migrations commit individually. A late failure can leave earlier committed steps plus a PENDING readiness marker; it is not an automatic schema rollback. Keep ingestion/activation held, record the failing safe code and exact run, and use the reviewed forward repair/retry procedure. Never auto-drop tables, erase migration history, reset roles or mark PASS manually. This workflow does not flip routing or claim full read/search activation.
